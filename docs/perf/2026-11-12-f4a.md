# F4a: Workspace Watcher, atribución y agregación (2026-11-12)

Referencias: [`SPEC.md`](../SPEC.md) §6.4.1–§6.4.2 (retención y agregación), §7 (Workspace Watcher), §11.4 (B6, B7) y §13.2 (G5, G7).

Ninguna medición toca `~/.claude` ni la base de datos real: las puertas usan la canalización real (`LivePipeline`: HTTP, `notify`, Git y SQLite) sobre carpetas temporales, con un registro de sesiones de prueba y un cliente HTTP que hace de mod. La prueba visual de la app se hizo contra una **copia** de `cockpit.db`.

Equipo: el mismo de F1–F3 (Windows 11, NTFS, Git 2.51.2.windows.1, toolchain GNU).

## M5 automatizado: Git no escribe en el repositorio

Test `git::tests::m5_reads_never_touch_the_index`. Prepara un repositorio con ficheros cuya información de `stat` en el índice está obsoleta (el caso en que Git querría refrescarlo), ejecuta tres veces cada lectura del `GitReader` (`rev-parse`, `status` con y sin no seguidos, `numstat`, diff de un fichero y `ls-files`) y comprueba que **ni el mtime ni el contenido** de `.git/index` cambian. Como control, un `git status` sin el endurecimiento sí lo reescribe: el test detecta la escritura.

**Hallazgo:** la primera versión falló. Aislando cada subcomando:

| Lectura (con `--no-optional-locks`) | ¿Reescribe `.git/index`? |
|---|---|
| `rev-parse --show-toplevel` | no |
| `status --porcelain=v2 -z --branch --untracked-files=all` | no |
| `diff --no-ext-diff --no-textconv --numstat -z HEAD` | **sí** |
| `diff --no-ext-diff --no-textconv --no-color HEAD -- <fichero>` | **sí** |
| `ls-files -z` | no |

La causa es `diff.autoRefreshIndex` (activado por defecto), que hace que `git diff` refresque el índice aunque lleve `--no-optional-locks`. Con `-c diff.autoRefreshIndex=false` en cada invocación el índice no cambia y la salida es idéntica (Git compara el contenido de los ficheros con `stat` obsoleto). Se añadió al endurecimiento obligatorio (SPEC §7.2, ADR 0007).

## G7: renombrados en NTFS

Método: `cargo run -p cockpit-ingest --release --example workspace_gates -- g7 salida.json`. Sobre un repositorio de 80 ficheros versionados, con una sesión viva, se renombra cada fichero con 120 ms de separación y se compara lo guardado en `file_events` con la verdad.

| Caso | Total | `renamed` con su origen | Borrado + creado |
|---|---|---|---|
| Mismo directorio | 40 | **40** | 0 |
| Entre carpetas, mismo nombre | 20 | **20** | 0 |
| Entre carpetas y con otro nombre | 20 | 0 | **20** |

**G7 resuelta, con matices:**

- **Dentro de un directorio**, `notify-debouncer-full` une el renombrado con su origen. Para ello no hace falta la `FileIdMap` recomendada (que recorre el árbol entero siguiendo enlaces al vigilar y con cada directorio nuevo): basta con la caché `PairCache`, que empareja cada `RENAMED_NEW_NAME` con el `RENAMED_OLD_NAME` anterior, como los entrega Windows.
- **Entre carpetas**, Windows no da un renombrado: entrega `REMOVED` + `ADDED`, y el debouncer no los une (ni con file-IDs). F4a los une si en el lote hay un único borrado y un único creado con el mismo nombre de fichero y a menos de 20 ms.
- **Si además cambia el nombre**, queda como borrado + creado sin `from`: es el respaldo previsto en G7.

## Guardado atómico de Claude Code

Medido con una sonda `fs.watch` sobre una carpeta temporal mientras esta misma sesión (Desktop 2.1.321) usaba `Edit` y `Write`:

```text
Edit (fichero existente)                    Write (fichero nuevo)
  rename  objetivo.txt.tmp.25984.82cb86f02ec0   rename  nuevo.txt.tmp.25984.8c30986bc5b7
  change  objetivo.txt.tmp.25984.82cb86f02ec0   change  nuevo.txt.tmp.25984.8c30986bc5b7
  change  objetivo.txt.tmp.25984.82cb86f02ec0   rename  nuevo.txt.tmp.25984.8c30986bc5b7
  rename  objetivo.txt          (borrado)       rename  nuevo.txt
  rename  objetivo.txt.tmp.25984.82cb86f02ec0
  rename  objetivo.txt
```

Claude Code escribe un temporal `<nombre>.tmp.<pid>.<hex>`, borra el original y renombra el temporal sobre él. La primera versión del Watcher lo mostraba como «renombrado de sí mismo». Ahora el temporal se descarta, los eventos de una misma ruta en un lote se reducen a uno según el estado final, y la diferencia entre `modified` y `created` sale de la fecha de creación, que NTFS conserva del fichero sustituido (*tunneling*). Test: `watcher::tests::claude_code_atomic_saves_are_single_changes`.

## G5: precisión de la atribución

Método: `cargo run -p cockpit-ingest --release --example workspace_gates -- g5 salida.json`. Repositorio temporal con dos sesiones vivas (A y B) en un registro de pruebas y un cliente HTTP que hace de mod. El mod envía cada lote 50 ms después de empezar la herramienta (`$.clock.after(50)`, §5.3). `Edit` y `Write` escriben como Claude Code (temporal + borrado + renombrado). Los `Bash` y los cambios externos escriben directamente. Cada fichero se toca una vez y la verdad se compara con la fila final de `file_events`, después de que todo se asiente.

Escenarios (256 cambios):

| Escenario | Cambios | Verdad |
|---|---|---|
| `edit`: `Edit`/`Write` de la sesión A | 74 | `claude`, esa herramienta |
| `edit_mod_tardío`: como el anterior, pero el mod envía a los 2,6–4 s (reconexión) | 16 | `claude`, esa herramienta |
| `bash`: `Bash` de la sesión B que escribe 2–3 ficheros en 0,5–2 s | 49 | `claude-shell`, ese `Bash` |
| `externo_sesión_activa`: cambios a mano con las sesiones vivas y sin herramientas | 30 | no Claude |
| `paralelo`: dos herramientas a la vez de la sesión A, cada una con su fichero | 24 | cada una el suyo |
| `dos_sesiones`: A y B editan a la vez en la misma raíz | 24 | cada una el suyo |
| `externo_durante_bash` (adverso): cambio a mano mientras corre un `Bash` de B | 8 | no Claude |
| `edit_vs_externo` / `externo_durante_edit` (adverso): cambio a mano 5–40 ms después de un `Edit` de A sobre otro fichero | 8 + 8 | `claude` / no Claude |
| `sin_sesión`: cambios a mano sin sesiones vivas | 15 | `external` |

Se cuenta como acierto la herramienta exacta para `claude`/`claude-shell`, y `unknown` o `external` para lo que no es de Claude.

### Primera pasada: reglas de §7.3 al pie de la letra

| Confianza | Aciertos | Precisión | Objetivo |
|---|---|---|---|
| `high` | 145 / 147 | 0,986 | ≥ 0,95 ✓ |
| `medium` | 11 / 15 | 0,733 | ≥ 0,80 ✗ |
| `low` | 68 / 94 | 0,723 | — |
| externos atribuidos a `claude` | **8** | | 0 ✗ |

Causas:

1. **R2 se lleva cambios ajenos.** Los 8 cambios externos escritos mientras Claude editaba otro fichero se atribuyeron a ese `Edit` (R2). Además, en `edit_mod_tardío` el cambio quedaba asentado con el `Edit` *anterior* (cuya cola δ lo cubría) y el aviso tardío ya no podía corregirlo, porque solo se permite subir desde `unknown`. Pero `Edit`/`Write` solo escriben su propio fichero: con una ruta conocida distinta, no pueden ser la causa.
2. **La cola δ empata con la herramienta en curso.** Entre dos `Bash` seguidos hay menos de 1,5 s, así que un cambio del segundo también cae en la cola δ del primero. Hay empate, gana el más reciente (bien) y la confianza baja a `low`: 38 de 49 cambios de `Bash` salieron `low`.
3. **Fallo del arnés:** tres ficheros se editaban dos veces y se comparaban con la fila de la otra edición. Corregido antes de la segunda pasada.

### Segunda pasada: con la calibración

Cambios (aceptados por el usuario el 2026-11-12, CHANGELOG): R2 solo para ediciones **sin ruta comparable**; primer desempate por el **intervalo real** `[started_at, finished_at]`; y una atribución definitiva puede **subir a R1** si gana confianza. ε = 250 ms y δ = 1.500 ms no cambian.

| Confianza | Aciertos | Precisión | Objetivo |
|---|---|---|---|
| `high` | 161 / 161 | **1,00** | ≥ 0,95 ✓ |
| `medium` | 49 / 57 | **0,86** | ≥ 0,80 ✓ |
| `low` | 38 / 38 | 1,00 | — |
| externos atribuidos a `claude` | **0** | | 0 ✓ |

Matriz verdad → actor asignado:

| Verdad \ actor | `claude` | `claude-shell` | `unknown` | `external` |
|---|---|---|---|---|
| `claude` (146) | **146** | 0 | 0 | 0 |
| `claude-shell` (49) | 0 | **49** | 0 | 0 |
| externo (61) | 0 | 8 | 38 | 15 |

Por escenario: `edit` 74/74 `claude·high`; `edit_mod_tardío` 16/16 `claude·high` (subidos a R1 al llegar el aviso tardío); `paralelo` 24/24 y `dos_sesiones` 24/24 `claude·high` con la herramienta exacta; `bash` 49/49 `claude-shell·medium`; `externo_sesión_activa` 30/30 y `externo_durante_edit` 8/8 `unknown·low`; `sin_sesión` 15/15 `external·high`.

**Lo que no se resuelve:** los 8 cambios a mano escritos mientras corría un `Bash` de la misma raíz salen como `claude-shell·medium`. Con solo el intervalo, un cambio externo durante un `Bash` no se distingue de uno del propio `Bash`; es el límite de R3 y por eso su confianza es `medium`. La precisión `medium` depende de cuántos cambios externos haya durante los `Bash`: en esta mezcla, 8 de 57.

**Calibración de ε y δ** (diferencia entre la hora del cambio y el intervalo real de su herramienta, 195 cambios de Claude):

| | mín | p50 | p95 | máx |
|---|---|---|---|---|
| cambio − inicio de la herramienta | 0 ms | 17 ms | 1.045 ms | 1.583 ms |
| cambio − fin de la herramienta | −1.338 ms | −11 ms | 0 ms | 1 ms |

Ningún cambio cae antes del inicio de su herramienta ni más de 1 ms después de su fin: ε = 250 ms y δ = 1.500 ms son holgados. No se reducen: la holgura cubre los `ToolFinished` del transcript (sin mod), que llegan con la hora de la línea de resultado, y con el desempate por intervalo real la cola δ ya no resta precisión.

**G5 resuelta**, con la calibración aceptada por el usuario (2026-11-12).

## B6 y B7: cambio → pintado y `numstat` → pintado

Método: `scripts/measure/workspace-cycle.ps1`, con el binario de release (`npm run tauri build -- --no-bundle`). La app arranca con todas las rutas redirigidas a una carpeta temporal (`DEV_COCKPIT_*`, sin `~/.claude` ni la base real) y con la ventana visible. `fs-ops.mjs` crea un repositorio de 100 ficheros, se registra como sesión viva con su propio PID y hace 350 operaciones separadas 150 ms: 100 creaciones, 100 modificaciones, 50 renombrados y 150 borrados. La interfaz anota con `perf_mark`:

- `file` (B6): la hora del primer evento crudo de un cambio nuevo frente al pintado;
- `numstat` (B7): el último cambio incluido en una consulta de Git frente al pintado. Como eso subestima la espera de los cambios anteriores del mismo lote, también se calcula **por operación**: para cada cambio, el primer `numstat` pintado que lo incluye.

| Medición | n | p50 | p95 | máx | Objetivo |
|---|---|---|---|---|---|
| **B6** cambio → pintado | 350 | 256 ms | **317 ms** | 350 ms | < 700 ms ✓ |
| B7, desde el último cambio incluido | 63 | 414 ms | 583 ms | 874 ms | — |
| **B7** por cambio | 350 | 874 ms | **1.189 ms** | 1.245 ms | < 1,5 s ✓ |

**Primera medición de B7, fallida:** con la coalescencia de 500 ms y un tope de 2 s contado desde que el hilo de Git recibía el aviso, B7 por cambio dio p50 de 1.478 ms y **p95 de 2.421 ms** (25 consultas en 52 s). Con actividad continua, un cambio que llegaba durante una consulta esperaba esa consulta, una ventana de 2 s y la siguiente. El tope pasó a 1 s **contado desde el primer cambio pendiente**, y se repitió la medición con el binario nuevo (tabla de arriba). B6 no cambió (p95 de 336 ms en la primera medición).

Es un repositorio pequeño: `git status` + `numstat` tardan unos 100–250 ms. En repos grandes (M4: `numstat` de hasta 687 ms), el p95 de B7 subirá en la misma medida.
